## Instructional Purpose

Help first-time Engineering Technology readers understand what placement-data fields mean physically.

The figure should answer:

> **What do X, Y, rotation, board side, and the component placement origin mean on an actual PCB?**

The figure should reinforce the Section 4.12 idea that a coordinate is only useful when the following conventions agree:

- coordinate origin;
- X/Y axis directions;
- units;
- component-library reference orientation;
- positive rotation convention;
- board side / viewing convention.

The artwork should complement, not duplicate, Table 4.12.1. The table teaches **data records**; this figure teaches **spatial interpretation**.

---

## Central Teaching Message

> **Placement coordinates are not self-explanatory. X/Y positions and rotation only have meaning relative to a defined board origin, axis directions, component-library orientation, and board-side convention.**

Supporting messages:

- a component's X/Y values locate its defined placement origin;
- rotation is measured relative to the package/library's reference orientation;
- the board origin can be defined at different valid locations depending on workflow;
- bottom-side interpretation must follow the configured CAD-to-machine convention;
- students should verify conventions rather than assume one universal scheme.

## Overall Layout

Use a **main top-side PCB coordinate diagram** occupying about 70-75% of the figure, plus a smaller **bottom-side convention inset** occupying about 25-30%.

Recommended composition:

### Main panel - Top-side placement coordinates

Show:

- one simplified rectangular PCB viewed from above;
- a clearly marked placement origin `O`;
- X and Y axes beginning at that origin;
- three representative component footprints/placements;
- reference designators such as `R12`, `C7`, and `U3`;
- one component-center/placement-origin crosshair;
- concise coordinate text near one or two example components;
- visible rotation cues such as `0°`, `90°`, and `180°`;
- a small reference-orientation marker on the package/library geometry.

Use the Section 4.12 representative table values if numerical labels are shown. Recommended examples:

- `R12: X=18.50 mm, Y=12.00 mm, 0°`
- `C7: X=22.15 mm, Y=12.00 mm, 90°`
- `U3: X=40.80 mm, Y=26.35 mm, 180°`

Do not force all three full numeric strings into the artwork if 900 px readability suffers. At least one complete X/Y/rotation example must remain.

### Bottom-side convention inset

Show a compact bottom-side concept, not a second complete board.

The inset should communicate:

- `Bottom side`;
- viewing/mirroring interpretation depends on the CAD-to-machine workflow;
- rotation and coordinates must be transformed according to the configured convention;
- students must **verify the convention**.

The inset should **not** present one specific mirror/rotation transform as universally correct. If a mirror arrow is shown, it must be labeled as an **example workflow transformation**, not a universal rule.

Suggested inset message:

`Bottom-side coordinates / rotation: verify the configured CAD ↔ machine convention`

## Required Technical Relationships

1. The X and Y axes must originate from the same defined board datum.
2. X and Y must be orthogonal.
3. Component X/Y coordinates must refer to a defined component placement origin, not an arbitrary package corner.
4. Rotation must be shown about the component placement axis/origin.
5. The visual must distinguish **reference designator** from **package/library orientation**.
6. The 0° reference must be presented as a library/workflow reference, not as a universal physical orientation. An orientation marker such as a notch or pin-1 cue should make this visually explicit.
7. The bottom-side inset must make convention dependence explicit.
8. The figure must not imply one universal positive-rotation direction across all CAD and placement systems.
9. The figure must not imply one universal bottom-side mirroring rule.
10. The figure must not imply that the board origin is always the lower-left corner; if lower-left is used for illustration, label it as **example placement origin** or otherwise state that origin location is workflow-defined.
11. The component's reference designator must identify the component instance; it must not be confused with package type.
12. If numerical data are used, they must match the representative Section 4.12 table.
13. No detailed machine programming or coordinate-transform mathematics should appear.

## Spatial / Geometry Requirements

- Use a true top view for the main coordinate panel.
- Keep the board rectangular and proportioned for easy reading rather than photographic realism.
- Place the example origin near a board corner for clarity, but explicitly show that it is the **defined example origin**.
- Keep X and Y arrowheads clear of component graphics.
- The component-placement-origin marker must sit at the center/reference point used by its X/Y callout.
- Rotation arrows must wrap around the intended component center and must not be mistaken for board rotation.
- The asymmetric IC should have a clear pin-1/notch/reference cue so 0°/90°/180° changes are visually meaningful.
- Keep reference-designator labels close to their associated component.
- Do not route leader lines through component bodies or axis labels.
- Keep the bottom-side inset visually separated from the main panel with its own border or light background.
- Maintain approximately **6-8% outer canvas margin**.
- If the numeric callout becomes crowded, reduce the number of numerical examples before reducing font size.
- Keep a clear no-label corridor along both coordinate axes so the arrows and axis letters remain unmistakable at 900 px.
- Do not place the bottom-side inset so close to the X/Y axes that it can be mistaken for part of the same coordinate frame.

## Technical-Verification Basis

### Current Section 4.12 basis

The current Section 4.12 Rev3 states that a basic placement record commonly includes:

- reference designator;
- X coordinate;
- Y coordinate;
- rotation;
- board side;
- package/component-library identifier.

It also states that X/Y positions depend on a defined coordinate origin and that rotation and bottom-side interpretation depend on package/library and CAD-to-machine conventions.

### Approved outline basis

The approved Section 4.12 outline explicitly requires:

- reference designator;
- X/Y coordinates;
- rotation;
- board side;
- package/library awareness;
- CAD/centroid/PnP data;
- coordinate origin.

### Primary instructional basis

MET406 Chapter 4 - Assembly Technologies, Pick-and-Place Assembly programming material teaches that placement data include:

- part/reference identifier;
- package type;
- X/Y center coordinates;
- rotation angle;
- top/bottom layer/side.

### Approved secondary/current verification basis already documented in Section 4.12

- Coombs, *Printed Circuits Handbook*: component placement list fields including reference designator, X/Y and rotation.
- Current placement-program workflows documented during Section 4.12 drafting confirm that CAD import, component descriptions, coordinate/orientation information, and board-side conventions are workflow-dependent.

No external figure should be reproduced.

2. add orthogonal X/Y axes;
3. place generic R/C/IC component shapes;

6. add rotation/orientation cues;
7. add one or two verified numerical coordinate examples from Table 4.12.1;
8. create the separate bottom-side convention inset;
9. render at 900 px;
10. freeze the strongest baseline and correct only specific issues.

If AI-generated imagery is used for an initial concept, do not rely on generated text, axis geometry, component angles, or numerical labels. Rebuild those elements as controlled vector geometry.
