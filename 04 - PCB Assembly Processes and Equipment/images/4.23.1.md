# Figure 4.23.1 Suggested Content - Manufacturing Job Package Connects Product Definition to Factory Setup

## Status

**Suggested-content specification - Rev1 QA-reviewed candidate**

This file defines the instructional content and generation constraints for Figure 4.23.1 in Section 4.23, **NPI and Manufacturing Job Package Basics**.

The figure has one instructional role: **show the information architecture of a manufacturing job package and how controlled manufacturing information enables factory setup/readiness**.

Do **not** call this specification or generated artwork canonical/final before explicit project-owner acceptance.

---

## Figure Title for Authoring / Reference Only

**Manufacturing Job Package Connects Product Definition to Factory Setup**

Do **not** place this overall title or figure number inside the artwork.

---

## Instructional Purpose

Show how a released product definition becomes a usable manufacturing information set for the factory.

The figure should organize the job package into the four functions used in Section 4.23:

1. **Product definition**
2. **Process definition**
3. **Verification definition**
4. **Configuration identity**

Then show how those controlled information groups support practical factory-readiness activities such as:

- material/tooling preparation;
- machine setup;
- operator/work-station instructions;
- setup/inspection readiness.

The figure should allow a beginning MET reader to answer:

> **What kinds of controlled information does the factory need before it can set up and run the assembly processes already learned in Chapter 4?**

---

## Central Teaching Message

> **The manufacturing job package controls what will be built, how the job will be processed, what must be verified, and which approved configuration applies.**

A secondary message should remain visually clear:

> **The job package is a controlled information set, not one universal file.**

## Overall Layout

Use a **three-stage left-to-right information architecture**.

### Left stage - released product definition

Show one compact source block labeled:

- `Released product definition`

Optional secondary label:

- `Part number / revision`

Use a generic document/data symbol only. Do not recreate Chapter 3's release-package consistency comparison.

### Center stage - manufacturing job package

Use one visually dominant rounded container labeled:

- `Manufacturing job package`

Inside it, show three primary information groups plus one clearly cross-cutting configuration band.

#### Product definition

Representative items:

- `BOM / approved parts`
- `Assembly drawing`
- `Placement / PnP data`
- `PCB / panel identity`

#### Process definition

Representative items:

- `Stencil / paste information`
- `Work instructions`
- `Traveler / router`
- `Machine programs / recipes`

#### Verification definition

Representative items:

- `Setup / first-board checks`
- `Inspection-plan information`
- `Test-plan awareness`
- `Hold / signoff points`

#### Configuration identity

Show this as a **full-width band beneath or around the other groups** so it visibly applies across the complete job package.

Representative items:

- `Product part number / revision`
- `Engineering-change status`
- `Controlled document / program IDs`

Optional restrained note at the bottom of the central container:

- `May be paper, files, database records, or integrated digital data`

This note is secondary and may be omitted if it reduces 900 px readability.

### Right stage - factory readiness / setup

Use four compact output blocks:

- `Material + tooling preparation`
- `Machine setup`
- `Operator / work-station instructions`
- `Setup / inspection readiness`

Use arrows from the **job package as a controlled set** to these readiness outputs.

Do not create an exhaustive many-to-many arrow matrix between every document and every factory activity.

## Required Technical Relationships

1. The **released product definition** must be upstream of the manufacturing job package.
2. The manufacturing job package must be shown as a **controlled information set**, not as a physical material input.
3. The four information functions must answer:
   - **what are we building?**
   - **how should this job be built?**
   - **what must be checked?**
   - **which approved configuration applies?**
4. `Configuration identity` must visually apply across the complete job package rather than look like an optional standalone document.
5. The figure must not imply that every factory uses the same file set, names, or document format.
6. The figure must not imply that every representative item must be a separate physical file.
7. The BOM must not appear to define placement location/orientation by itself.
8. The assembly drawing must not be represented as machine-readable placement data.
9. Placement/PnP data must remain one controlled input within the larger package; detailed coordinate/origin/fiducial teaching remains Section 4.12.
10. Machine programs/recipes must appear as equipment-specific controlled manufacturing information, not as identical copies of design-source files.
11. Inspection/test-plan information must be shown as **readiness information**, not as a final product acceptance result.
12. The right side must show **factory readiness/setup**, not the physical SMT/THT process sequence.
13. The figure must not duplicate Chapter 3 Figure 3.14.3's good/bad release-revision mismatch comparison.
14. The figure must not extend into Section 4.24's physical line-side identity checks or Section 4.25's detailed first-board execution.

## Spatial / Geometry Requirements

- Maintain a clear left-to-right reading direction.
- Make the central job-package container the largest object in the figure.
- Use a balanced three-group upper structure with a full-width `Configuration identity` band beneath it, or an equivalent arrangement that clearly shows cross-cutting configuration control.
- Use one primary arrow from the released product definition to the job package.
- Use four clean arrows from the job package to the readiness outputs.
- Keep the right-side readiness outputs vertically aligned or arranged in a clean 2x2 grid.
- Avoid arrow crossings.
- Keep internal representative-item text subordinate to the group headings.
- Keep all text horizontal.
- Use approximately **5-7% outer margins** and comfortable internal padding.
- Do not show a physical PCBA moving through the diagram; this is an **information-architecture** figure.
- No text may touch box borders, arrows, or icons.
- Leader/connector lines must terminate clearly at their intended blocks.

## Scope Boundaries

This figure **should show**:

- released product definition as the upstream controlled source;
- the four job-package information functions;
- representative controlled items within those functions;
- configuration identity as a cross-cutting requirement;
- the connection from controlled information to factory readiness/setup.

It should **not show**:

- detailed BOM columns or purchasing workflows;
- detailed AML/AVL database architecture;
- physical reel/tray/tube identity, quantity, lot/date-code, barcode, feeder location, paste status, or MSL checks from Section 4.24;
- detailed first-board execution from Section 4.25;
- detailed placement coordinate conventions/fiducials from Section 4.12;
- detailed machine parameter development;
- inspection/test method selection or acceptance criteria from Chapter 5;
- MES genealogy, MRB, CAPA, formal calibration, or enterprise quality-system workflows;
- formal regulated-industry FAI requirements;
- numerical process settings or acceptance limits.

## Editable SVG Requirements

Use a **true editable SVG** as the controlled source whenever practical. Do not place a raster image inside an SVG wrapper as the primary artwork.

Required SVG properties:

- explicit `width`, `height`, and `viewBox`;
- `preserveAspectRatio="xMidYMid meet"`;
- an explicit full-canvas white rectangle as the first visible drawing element, for example `<rect x="0" y="0" width="100%" height="100%" fill="#ffffff"/>`;
- editable text rather than outlined text where practical;
- separate editable vector objects/groups for the released-product block, each information group, configuration band, readiness outputs, arrows, icons, and labels;
- `markerUnits="userSpaceOnUse"` for normal engineering/information arrows unless there is a specific technical reason to scale an arrowhead with stroke width;
- no external fonts, externally linked artwork, embedded vendor graphics, or raster artwork as the primary composition;
- content-first canvas sizing: expand or reshape the canvas before shrinking important text excessively.

A technically valid SVG render is **not** sufficient. The candidate must pass a dedicated visual geometry/layout gate:

- every text block fits comfortably inside its intended region;
- no text touches or crosses a box/panel boundary;
- no major objects overlap unintentionally;
- arrows terminate clearly at intended targets;
- arrows do not pass through unrelated text or objects;
- group alignment is clean enough for textbook publication;
- outer margins and internal padding are balanced;
- any wording, font-size, box-size, object-position, arrow-routing, or canvas-size change triggers another layout QA pass.

Render and visually inspect at:

- native authoring size;
- approximately 1600 px width;
- approximately 1200 px width;
- approximately 900 px mdBook width.

The final candidate SVG must remain editable after all QA corrections.

Recommended editable groups:

- released product definition;
- product-definition group;
- process-definition group;
- verification-definition group;
- configuration-identity band;
- each readiness-output block;
- icons;
- connectors/arrows;
- labels.
