## Suggested Content for Figure 3.13.4

### Figure title for authoring/reference only

`Conveyor Rail and Board-Support Access`

### Instructional purpose

Show that an assembly panel must provide physical regions for:

- conveyor/edge handling;
- clamps or guides;
- underside board support.

The figure should compare a workable panel with one where component placement blocks those manufacturing interfaces.

### Central teaching message

> **A panel needs usable edge-handling and support regions. Components and panel geometry can unintentionally interfere with conveyors, clamps, rails, or underside supports.**

### Canonical PNG filename

`3.13.4 - Conveyor Rail and Board-Support Access.png`

### Intended mdBook display width

`900 px`

### Recommended canvas size / aspect ratio

- Authoring canvas: approximately `1800 x 1050 px`.
- Recommended aspect ratio: approximately `12:7` to `16:9`.
- Use a matched good-versus-restricted comparison with a top/side hybrid if needed.

### Overall layout

Use two panels:

Left:
- `Handling and support access available`

Right:
- `Handling or support access blocked`

Each panel should show:
- panel/PCB edge resting in or above a simple conveyor-rail/guide representation;
- edge handling region;
- underside support-point locations beneath the board.

Good case:
- no component overhang into the rail/conveyor region;
- underside support points contact clear PCB areas.

Restricted case:
- one overhanging edge component enters the rail/conveyor region;
- one or more bottom-side components occupy the intended support locations.

### Required objects and labels

Required labels:

- `Conveyor / handling rail`
- `Clear edge region`
- `Overhanging component`
- `Underside support point`
- `Bottom-side component`
- `Support area blocked`

Optional:
- `Panel rail`
- `Clamp / guide region`

A green check / red X may be used sparingly.

### Required technical relationships

- Good-case panel edge must physically align with the conveyor/handling rail.
- Edge component in the poor case must actually intrude into the handling region, not merely sit near it.
- Support point in the good case must contact a clear underside board area.
- Bottom-side component in the poor case must occupy the intended support location and visibly prevent contact.
- Do not imply that support pins must always be in the same location.
- Do not imply one universal conveyor width or edge-clearance dimension.
- Do not imply that bottom-side components are generally prohibited; the lesson is to preserve a feasible support strategy or coordinate custom support tooling.

### Spatial / geometry requirements

- Keep board/panel scale matched between the two panels.
- Use a simplified side/profile cue for conveyor interference and a simple underside or cutaway inset if needed for support access. The board top/bottom relationship must remain visually unambiguous.
- If using support pins, show them as generic vertical cylinders or posts.
- Ensure poor-case bottom-side component is clearly beneath the board rather than on the top surface.
- Avoid visual ambiguity between panel rail and conveyor rail; label both if both appear.
- Keep the critical interference visible at 900 px.


### Color / style guidance

- Clean engineering-textbook appearance consistent with the current EPAC figure set.
- Explicit white background; no transparent-canvas dependence.
- Flat 2D top-view, side-view, or restrained schematic/isometric geometry only where it improves physical understanding.
- Restrained engineering palette:
  - green/blue-green PCB areas;
  - neutral gray panel rails, fixtures, tools, and mechanical features;
  - copper/gold for exposed copper or fiducial targets;
  - muted blue for normal paths/alignment/handling arrows;
  - limited orange/red only for break zones, keep-outs, or interference/problem conditions.
- Sans-serif labels sized for the 900 px mdBook render.
- Moderate line weights and consistent visual hierarchy.
- No decorative gradients, glossy rendering, dramatic shadows, logos, watermarks, or branded commercial products.
- Do not rely on color alone; use geometry, line style, labels, arrows, and good/bad structure.
- Do not embed the external figure number, final caption, or an oversized duplicate overall title inside the artwork.


### Scope boundaries

This figure should **not** teach:

- conveyor machine design;
- conveyor width/speed;
- clamp-force calculations;
- detailed support-fixture design;
- pin-grid optimization;
- stencil-printer underside-tooling design;
- pick-and-place machine programming;
- exact process-rail dimensions.

Figure 3.13.1 owns overall panel anatomy.  
Figure 3.13.2 owns separation geometry.  
Figure 3.13.3 owns fiducial alignment.

### Technical-verification basis

Use as grounding:

- current Section 3.13.7;
- Coombs conveyed-edge/tooling analysis;
- current supplier guidance on assembly rails/process edges;
- primary Chapter 3 concept that automated tooling and handling need edge space;
- current section statement that bottom-side components can occupy regions needed for support.

No universal support-pin or conveyor-edge dimension should appear.

### Originality / copyright requirements

Create an original generic assembly-handling/support comparison.

Do not:

- copy conveyor-machine photographs;
- trace stencil-printer support fixtures;
- reproduce a vendor support-pin drawing;
- use branded machines or proprietary fixture layouts.

Use independently drawn generic rail, board, component, and support geometry.

### Editable SVG requirements

The strongest final candidate should include both a publication PNG and a **true editable SVG**.

The SVG must:

- use vector geometry rather than an embedded raster image as the primary artwork;
- keep text editable where practical;
- keep panel rails, PCB images, score lines, tabs, holes, fiducials, support points, arrows, leaders, and labels as separate editable objects;
- define explicit `width`, `height`, and `viewBox` values;
- use `preserveAspectRatio="xMidYMid meet"`;
- include an explicit full-canvas white rectangle as the first visible drawing element, e.g. `<rect x="0" y="0" width="100%" height="100%" fill="#ffffff"/>`;
- preserve adequate safe margins so no rail, feature, arrow, or label is clipped;
- use `markerUnits="userSpaceOnUse"` for normal engineering arrows unless a specific technical reason requires otherwise;
- remain clear when rendered at native size and approximately 1600 px, 1200 px, and 900 px width.

Before recommendation, render-check the final SVG at all four sizes.
