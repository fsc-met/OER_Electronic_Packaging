## Suggested Content for Figure 3.14.3

### Figure title for authoring/reference only

`Release Package Revision Consistency`

### Instructional purpose

Show that manufacturing readiness depends on the **complete released set** describing one approved product definition and revision.

The figure should make a common failure mode visually obvious:

> several individual files may each look valid, yet the package is inconsistent because one artifact is stale or belongs to another revision.

### Central teaching message

> **A release package is controlled as a set. All applicable outputs must come from and describe the same approved product definition and revision.**

### Canonical PNG filename

`3.14.3 - Release Package Revision Consistency.png`

### Intended mdBook display width

`900 px`

### Recommended canvas size / aspect ratio

- Authoring canvas: approximately `1800 x 1050 px`.
- Recommended aspect ratio: approximately `12:7` to `16:9`.
- Use a matched two-panel comparison:
  - `Consistent release package`
  - `Inconsistent release package`

### Overall layout

Use two side-by-side panels with the same generic product/source at the top.

#### Left panel — consistent

Top source box:

- `Approved PCB product definition`
- `Part number: P/N 1234`
- `Revision C`

Arrows feed several **applicable release artifacts**, each labeled `Rev C`:

- `Fabrication data`
- `Drill / profile data`
- `BOM`
- `Component-placement data`
- `Assembly drawing / notes`
- `Paste / stencil data (if applicable)`

Bottom state:

- `Consistent package`
- green check

#### Right panel — inconsistent

Use the same approved source:

- `P/N 1234`
- `Revision C`

Most artifacts are `Rev C`, but one artifact is stale, for example:

- `BOM — Rev B`

or:

- `Placement data — Rev B`

Mark that artifact with a red outline/X and retain its normal document shape so the teaching point is package inconsistency rather than file corruption.

Bottom state:

- `Inconsistent package`
- `Release blocked until corrected`

Add a small qualifier:

`Exact artifact set varies by product and supplier.`

### Required objects and labels

Required labels:

- `Approved PCB product definition`
- `Part number`
- `Revision`
- `Applicable release artifacts`
- `Fabrication data`
- `Drill / profile data`
- `BOM`
- `Component-placement data`
- `Assembly drawing / notes`
- `Paste / stencil data (if applicable)`
- `Consistent package`
- `Inconsistent package`
- `Release blocked until corrected`

Use simple generic document/folder icons if helpful.

### Required technical relationships

- All left-panel artifacts must visibly reference the same revision as the approved source.
- The right-panel source remains the approved current revision.
- Exactly one or at most two artifacts should be shown stale/mismatched; do not clutter the lesson with many failures.
- The stale artifact must still look like a plausible individual document, reinforcing that a file can be individually valid yet wrong for the package.
- The mismatch must block release until corrected.
- Do not imply that every organization always releases every artifact shown.
- `Paste / stencil data` must be explicitly labeled `if applicable`.
- The figure should emphasize **revision/product-definition consistency**, not detailed data formats.
- A changed source should conceptually require affected outputs to be regenerated, but do not duplicate the Figure 3.14.2 recheck loop.

### Spatial / geometry requirements

- Keep the two panels visually matched.
- Use the same artifact positions in both panels so the mismatch is immediately obvious.
- Use one common source box at the top of each panel with arrows fanning out to the artifacts. The arrows should represent derivation/control from the approved source, not a manufacturing-process sequence.
- Keep artifact labels short.
- Put the revision identifier (`Rev C`, `Rev B`) in a consistent location on each artifact.
- Use green only for the consistent state and red only for the stale/mismatch state.
- Avoid tiny filenames or file extensions.
- Avoid showing specific Gerber layer names or proprietary manufacturing-data structures.


### Color / style guidance

- Clean engineering-textbook appearance consistent with the current EPAC figure set.
- Explicit white background; never rely on viewer transparency/default canvas color.
- Flat 2D vector/schematic style rather than photorealistic software screenshots.
- Restrained engineering palette:
  - blue/blue-gray for normal review/check paths;
  - neutral gray for controlled documents, review frames, and secondary objects;
  - muted green for acceptable/closed/consistent states;
  - muted orange for caution or engineering-review states;
  - limited red only for mismatches, unresolved findings, or blocked release states.
- Sans-serif labels sized for the 900 px mdBook render.
- Moderate line weights and consistent visual hierarchy.
- Do not rely on color alone; pair color with labels, arrows, line style, symbols, or panel structure.
- No decorative gradients, glossy rendering, vendor logos, software UI chrome, watermarks, or branded screenshots.
- Do not embed the external figure number, final caption, or an oversized duplicate overall title inside the artwork.

- Gerber/ODB++/IPC-2581 structure;
- drill-file syntax;
- BOM column definitions;
- centroid-file column definitions;
- CAM layer mapping;
- supplier upload procedure;
- detailed configuration-management software;
- detailed ECO workflow.

Chapter 2.13 owns manufacturing-data-format detail.  
Figure 3.14.2 owns change/recheck disposition.

### Originality / copyright requirements

Create an original generic release-package consistency diagram.

Do not:

- reproduce a PLM/PDM/ERP software screenshot;
- copy a supplier upload portal;
- trace document-control icons from commercial software;
- use real customer part numbers, filenames, drawings, or BOMs.

Use simple independently drawn generic document/folder symbols and fictitious identifiers such as `P/N 1234, Rev C`.


### Generation guidance

Use a controlled technical-figure workflow.

1. Establish the instructional composition from this specification.
2. If AI image generation is used for an early concept, preserve it as a concept revision only.
3. Once a promising visual baseline exists, freeze the overall visual language.
4. Make targeted corrections only; do not redesign correct portions unless the underlying concept is wrong.
5. Prefer controlled SVG/vector rebuilding when text, flow logic, branch geometry, revision labels, or arrows cannot be controlled reliably in raster generation.
6. Verify every word, arrow, leader, branch, state, and revision label after each meaningful revision.
7. Preserve every meaningful revision under a new filename.
8. Do not copy/rename a candidate to the canonical publication filename until explicit project-owner acceptance.



### Editable SVG requirements

The strongest final candidate should include both a publication PNG and a **true editable SVG**.

The SVG must:

- use vector geometry rather than an embedded raster image as the primary artwork;
- keep text editable where practical;
- keep boxes, arrows, flow branches, document icons, revision labels, callouts, and status symbols as separate editable objects;
- define explicit `width`, `height`, and `viewBox` values;
- use `preserveAspectRatio="xMidYMid meet"`;
- include an explicit full-canvas white rectangle as the first visible drawing element, for example `<rect x="0" y="0" width="100%" height="100%" fill="#ffffff"/>`;
- preserve adequate safe margins so no arrowhead, label, box, or artifact icon is clipped;
- use `markerUnits="userSpaceOnUse"` for normal engineering/process arrows unless a specific technical reason requires otherwise;
- remain clear when rendered at native size and approximately 1600 px, 1200 px, and 900 px width.

Before recommendation, render-check the final SVG at all four sizes.
