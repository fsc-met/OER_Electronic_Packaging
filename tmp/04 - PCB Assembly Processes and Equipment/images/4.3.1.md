## Suggested Content for Figure 4.3.1

### Figure title for authoring/reference only

`Manufacturing Job Package Connects Product Definition to Factory Setup`

### Instructional purpose

Show how a controlled manufacturing job package translates a released product definition into information the factory can actually use to prepare and verify a PCB assembly job.

The figure should organize the job package into the four functional information groups used in Section 4.3:

1. **Product definition**
2. **Process definition**
3. **Verification definition**
4. **Configuration identity**

It should then show how these controlled information groups support four practical manufacturing-readiness outputs:

- material preparation;
- machine and tooling setup;
- operator/work-station instructions;
- inspection/test readiness.

The figure should help the reader understand that a manufacturing job package is **not one universal file** and is **not simply a copy of the design release**. It is a controlled set of information that connects the approved product definition to factory execution.

### Central teaching message

> **The manufacturing job package controls what will be built, how the job will be processed, what must be verified, and which approved configuration applies.**

A second message should remain visually clear:

> **The job package may contain multiple documents, files, programs, or digital records; what matters is that the applicable information is complete, internally consistent, controlled, and usable by manufacturing.**

### Overall layout

Use a **three-stage left-to-right information architecture**.

#### Left stage — released product definition

Show one compact source block labeled:

`Released product definition`

Optional small sublabels:

- `Part number / revision`
- `Design release`

This block is only the upstream source. Do not recreate Chapter 3 Figure 3.14.3's consistent-versus-inconsistent release-package comparison.

#### Center stage — manufacturing job package

Use one visually dominant rounded container labeled:

`Manufacturing job package`

Inside it, arrange three primary content groups plus one clearly cross-cutting configuration-control band:

1. `Product definition`
2. `Process definition`
3. `Verification definition`
4. `Configuration identity` — shown as a full-width band beneath or around the other groups so it visibly applies to the entire job package rather than appearing to be an unrelated fourth document category.

Each group should contain only a few representative items.

Recommended representative content:

**Product definition**
- `BOM / approved parts`
- `Assembly drawing`
- `Placement data`
- `PCB / panel ID`

**Process definition**
- `Work instructions`
- `Traveler / router`
- `Machine programs / recipes`
- `Stencil / paste / handling notes`

**Verification definition**
- `Setup / first-board checks`
- `Inspection-plan information`
- `Test-plan awareness`
- `Hold / signoff points`

**Configuration identity**
- `Product part number`
- `Released revision`
- `Change status`
- `Controlled document / program IDs`

At the bottom of the central container, include one restrained note:

`May be paper, files, database records, or integrated digital data`

This note should be secondary and must not become the figure's focus.

#### Right stage — factory readiness / setup

Show four compact output blocks:

- `Material preparation`
- `Machine + tooling setup`
- `Operator / work-station instructions`
- `Inspection / test readiness`

Use arrows from the **job package as a controlled set** to these output blocks.

Do not draw one-to-one arrows from every individual document to every factory activity; the purpose is to show controlled information architecture, not an exhaustive dependency matrix.

### Required technical relationships

- The **released product definition** is upstream of the manufacturing job package.
- The manufacturing job package must be shown as a **controlled information set**, not as a physical material input.
- The job package must contain or reference information that answers:
  - what is being built;
  - how it should be built;
  - what must be verified;
  - which approved configuration applies.
- `Configuration identity` must visually apply across the job package. It must not look like an unrelated optional file.
- The figure must not imply that every company uses the exact same file set, names, or document format.
- The figure must not imply that every listed item must exist as a separate standalone file.
- The figure must not imply that a BOM alone defines the complete assembly.
- The figure must not imply that an assembly drawing is machine placement data.
- The figure must not imply that machine programs/recipes are automatically identical to design-source files.
- The figure must not imply that inspection/test information is itself a product-acceptance result.
- The job package must drive factory **readiness/setup**, not be shown as the physical PCBA manufacturing process itself.
- The figure must not imply that a visually complete package is automatically valid; configuration identity and consistency are necessary.
- Do not reproduce the Chapter 3 release-package mismatch comparison; Section 4.3 focuses on manufacturing translation and setup.

### Generation guidance

A **controlled SVG/vector-first workflow is strongly preferred** because the figure depends on exact terminology and information relationships.

Recommended workflow:

1. Build the three-stage composition first.
2. Establish the central three-group job-package structure plus a cross-cutting configuration-identity band.
3. Add only the minimum representative items needed to distinguish the four information groups.
4. Add the four factory-readiness outputs.
5. Verify that the central diagram remains readable at 900 px.
6. Verify that no individual item appears to be the sole source of factory readiness.
7. If an AI-generated concept is used, treat it only as a layout concept unless all text and relationships are correct.
8. Once a strong visual baseline exists, freeze:
   - layout;
   - aspect ratio;
   - palette;
   - typography;
   - internal grid;
   - icon style;
   - arrow structure.
9. Make targeted corrections only.
10. Preserve every meaningful PNG/SVG revision with a different filename.
11. Do not create/copy the canonical publication filename until explicit project-owner acceptance.
