## Suggested Content for Figure 4.3.2

### Figure title for authoring/reference only

`NPI Build Readiness Loop from Released Revision to Controlled Production`

### Instructional purpose

Show NPI as an **iterative manufacturing-readiness process**, not a one-way handoff.

The figure should connect:

- released product revision;
- manufacturing-data review;
- job-package / machine-program preparation;
- material, tooling, and equipment readiness;
- an initial/prototype/pilot build as applicable;
- first-board / setup verification;
- a decision on whether the required checks are satisfied;
- controlled correction or engineering change when they are not;
- authorization to proceed to the next production stage when they are.

The figure should help readers understand why an NPI problem should feed back through controlled information and readiness checks rather than be "fixed" by an undocumented shop-floor workaround.

### Central teaching message

> **NPI turns a released product revision into a controlled manufacturing job through readiness review, build/setup verification, controlled correction when needed, and authorization to proceed.**

A second message should remain clear:

> **If an issue changes controlled product or manufacturing information, the affected source/output must be updated and rechecked before production continues.**

### Overall layout

Use a **left-to-right main readiness path** with one explicit feedback loop.

Recommended main path:

`Released product revision`
→
`Manufacturing-data review`
→
`Job package + programs prepared`
→
`Material / tooling / equipment readiness`
→
`Initial build / staged build as applicable`
→
`First-board / setup verification`
→
decision:
`Required checks satisfied?`

From the decision:

- **YES** branch → `Proceed to next authorized production stage`
- **NO / issue found** branch → `Controlled correction / engineering change`

The correction block should then flow to:

`Update affected controlled information / outputs`

and return to:

`Manufacturing-data review` or a clearly labeled `Readiness review`

This must be an obvious controlled loop, not a shortcut directly back into production.

### Required objects and labels

#### Main path

Required labels:

- `Released product revision`
- `Manufacturing-data review`
- `Job package + programs prepared`
- `Material / tooling / equipment readiness`
- `Initial build / staged build as applicable`
- `First-board / setup verification`
- `Required checks satisfied?`
- `Proceed to next authorized production stage`

#### Feedback loop

Required labels:

- `Issue found`
- `Controlled correction / engineering change`
- `Update affected controlled information / outputs`
- `Recheck readiness`

The exact geometry of `Recheck readiness` may be a small loop label rather than a separate box if needed for clarity.

#### Optional small qualification note

One small note may appear near the build/verification portion:

`Formality depends on product, customer, industry, and organization`

This note must remain secondary and should be omitted if it reduces 900 px readability.

### Required technical relationships

- The process must begin from a **released product revision**, not an uncontrolled design draft.
- Manufacturing-data review must occur before factory setup is treated as ready.
- Job-package and equipment-program preparation must occur before the initial build/setup verification.
- Material/tooling/equipment readiness must be established before the build is allowed to proceed.
- The figure must not imply that **prototype**, **pilot**, and **first article** are universally required as three separate sequential stages.
- The build-stage box should explicitly use `as applicable` or equivalent wording. A small secondary label may mention `prototype / pilot` as examples, but the main label should not imply that those terms are universal mandatory stages.
- First-board/setup verification must occur before the main `YES` authorization branch.
- A failed verification or discovered issue must not go directly to routine production.
- `Controlled correction / engineering change` must be shown as controlled work.
- A correction that affects controlled information must update the affected source/output before readiness is rechecked.
- The feedback loop must return to review/readiness, not bypass verification.
- The `YES` branch must say `next authorized production stage` rather than `full production`, because the authorized next step may be another pilot, qualification stage, limited run, or routine production depending on the organization.
- The figure must not imply that every shop uses the same NPI terminology or approval gates.
- The figure must not equate a practical PCB-assembly first-board check with a formal regulated-industry First Article Inspection requirement.
- The figure must not imply that prototype success automatically qualifies the production process.
- The figure must not show an undocumented shop-floor workaround as an acceptable branch.

### Decision / arrow semantics

Use simple, explicit line semantics:

- **solid navy arrows** = controlled forward readiness path;
- **green or dark-teal YES arrow** = authorization to proceed;
- **muted amber/red-orange NO/issue arrow** = issue requiring controlled action;
- **dashed or solid blue-gray feedback arrow** = return to readiness review after controlled update.

Do not use red as a decorative accent; reserve issue colors for the problem/correction path.

Use clear `YES` and `NO / issue found` labels at the decision split.

### Spatial / geometry requirements

- Use a left-to-right main path.
- Keep the released revision at the far left.
- Place the decision diamond or decision block near the right side.
- Place `Proceed to next authorized production stage` on the upper-right or direct-right YES branch.
- Place the correction/update path below the main sequence so the feedback loop can return leftward without crossing the forward path.
- Make the feedback arrow return to `Manufacturing-data review` or `Readiness review`.
- Do not return the loop directly to the initial build box.
- Avoid crossed arrows.
- Keep at least 4–5% safe outer margins.
- Keep all text horizontal.
- Use no more than two or three lines in each process box.
- Use a compact build-stage treatment such as:
  - `Initial / staged build`
  - secondary sublabel: `prototype / pilot as applicable`
- Make the decision text large enough to read at 900 px.
- Keep `YES` and `NO / issue found` labels visually close to their respective outgoing arrows.
